# PRD: chatwoot_crm

Статусы этапа: `todo` → `in progress` → `ready for review` → `pass` | `changes requested` | `blocked (H#)`.
Чек-боксы задач отмечает исполнитель. Критерии приёмки проверяют исполнитель (сам) и ревьюер (независимо).
Блокеры от человека обозначены `[H#]` и описаны в `crm/HUMAN.md`.

## Цели

- G1. Ни одно входящее сообщение клиента не теряется: уведомление в Telegram за ≤1 минуту, эскалация, если нет
  ответа.
- G2. Бесшовная передача клиента фрилансеру: тот же номер, тот же чат, вся история видна фрилансеру.
- G3. Фрилансер видит только диалоги своего номера и не видит телефон клиента. Менеджеры и админ видят всё.
- G4. Self-hosted, без WhatsApp Business и Meta, без лишних сторонних сервисов.
- G5. Задел под ИИ-ответы в нерабочее время.

## Не цели (сейчас)

- Полноценная CRM-воронка. Используем метки и атрибуты Chatwoot, дорабатываем по мере надобности.
- Массовые рассылки, исходящий холодный обзвон или переписка.
- Высокая доступность. Нагрузка маленькая: единицы номеров, до ~20 агентов, сотни диалогов в день.
- Переделка фронтенда сверх необходимого (скрытие номера, наши настройки).

## Сквозные требования

- NFR1. Чистый сервер после `script/crm/provision.sh` поднимается `kamal setup` по `crm/docs/runbook.md`.
- NFR2. Перезагрузка сервера → всё поднимается само, сессии WhatsApp сохраняются.
- NFR3. Версии зафиксированы. Обновление upstream и деплой — по процедуре в `crm/docs/runbook.md`.
- NFR4. Секретов в репозитории нет.
- NFR5. Часовой пояс рабочих часов (`CRM_BUSINESS_TZ`) и пороги эскалаций настраиваются, значения из H4.
- NFR6. Память: весь стек в покое ≤1.3 ГБ RAM (`docker stats`), под типичной нагрузкой без OOM на сервере
  2 ГБ + swap.
- NFR7. Наш код живёт в `custom/` и `spec/custom/`. Каждая правка upstream-файла есть в
  `crm/docs/core-changes.md`.

## Этап 5. Уведомления, эскалации, мониторинг — `todo` · `[H4]`

Всё внутри форка в `custom/`: listener на события через `Custom::AsyncDispatcher`, Sidekiq-jobs, расписание
через sidekiq-cron (по возможности без правки `config/schedule.yml`: подгрузка своего расписания из
`custom/config/`). Настройки — через ENV (или `InstallationConfig`, если удобнее админу), секреты (токен бота)
только через ENV.

Функции:
- [ ] **F5.1 Новое входящее** (`message_created`, incoming, не private) → сообщение в Telegram-группу: inbox
      (фрилансер), имя клиента, первые ~200 символов, ссылка на диалог. Телефона клиента нет. Серия сообщений
      одного диалога за 60 секунд склеивается в одно уведомление.
- [ ] **F5.2 Личные уведомления** назначенному агенту, если у него привязан Telegram. Привязка: `/start <код>`,
      код генерируется в профиле агента (небольшая доработка UI или rake-задача — выбрать проще). Хранить
      `telegram_chat_id` у пользователя (своя таблица в custom-миграции или `custom_attributes`, обосновать).
- [ ] **F5.3 Эскалации:** нет ответа за `CRM_ESCALATE_AFTER_MIN` (10) в рабочее время или
      `CRM_ESCALATE_AFTER_MIN_OFFHOURS` (60) вне его → алерт ⚠️ с упоминанием ответственных. Вторая ступень —
      через 2× времени. Ответ отменяет эскалации. Перед отправкой проверять актуальное состояние, без гонок.
      Если на этапе 0 нашёлся переиспользуемый механизм upstream, строить на нём.
- [ ] **F5.4 Мониторинг номеров:** cron каждые 2 минуты опрашивает Evolution о состоянии instance'ов, алерт
      при переходе в не-`open` (один раз на инцидент) и «восстановлено». Сводка в 10:00 `CRM_BUSINESS_TZ`:
      номера, неназначенные диалоги, диалоги без ответа больше 24 часов.
- [ ] **F5.5 Watchdog на хосте:** `script/crm/watchdog.sh` + systemd timer (раз в минуту): проверяет healthcheck
      web и «пульс» Sidekiq (cron-job пишет heartbeat, web отдаёт его на защищённом эндпоинте или скрипт
      читает через `docker exec`). При проблеме шлёт алерт прямо в Telegram API через `curl`, один раз на
      инцидент. Внешний пингер — по решению H9.
- [ ] **F5.6 Команды бота** (только привязанным админам): `/status`, `/mute <минуты>` для эскалаций. Получение
      апдейтов — `getUpdates` по cron (без публичного вебхука, чтобы Telegram не знал домен).
- [ ] Идемпотентность (повтор события не даёт дубля), ретраи Telegram с backoff (стандартный механизм Sidekiq),
      I18n-тексты (ru по умолчанию).
- [ ] Спеки в `spec/custom`: listener, склейка, эскалации (time travel), идемпотентность, мониторинг (стаб
      Evolution), команды бота (стаб Telegram).
- [ ] `crm/docs/runbook.md`: раздел «Уведомления и watchdog».

Критерии приёмки:
- AC5.1 Тестовое входящее → уведомление в Telegram-группе за ≤60 секунд, без телефона клиента.
- AC5.2 Эскалация приходит вовремя (для теста порог 1–2 минуты через ENV), после ответа новых эскалаций нет.
- AC5.3 Остановка Evolution → алерт ≤5 минут → «восстановлено» после запуска.
- AC5.4 Остановка роли sidekiq или web → алерт watchdog ≤3 минут.
- AC5.5 Повтор события не даёт дубля.
- AC5.6 `spec/custom` зелёный в CI, rubocop чистый, правки upstream в реестре.
