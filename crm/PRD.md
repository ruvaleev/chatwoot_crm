# PRD: chatwoot_crm

Статусы этапа: `todo` → `in progress` → `ready for review` → `pass` | `changes requested` | `blocked (H#)`.
Чек-боксы задач отмечает исполнитель. Критерии приёмки проверяют исполнитель (сам) и ревьюер (независимо).
Блокеры от человека обозначены `[H#]` и описаны в `crm/HUMAN.md`.

## Цели

- G1. Ни одно входящее сообщение клиента не теряется: уведомление в Telegram за ≤1 минуту, эскалация, если нет
  ответа.
- G2. Бесшовная передача клиента фрилансеру: тот же номер, тот же чат, вся история видна фрилансеру.
- G3. Фрилансер видит только диалоги, назначенные на него (или где он участник), и не видит телефон клиента.
  Менеджеры и админ видят всё.
- G4. Self-hosted, без WhatsApp Business и Meta, без лишних сторонних сервисов.
- G5. Задел под ИИ-ответы в нерабочее время.

## Не цели (сейчас)

- Полноценная CRM-воронка. Используем метки и атрибуты Chatwoot, дорабатываем по мере надобности.
- Массовые рассылки, исходящий холодный обзвон или переписка.
- Высокая доступность. Нагрузка маленькая: единицы номеров, до ~20 агентов, сотни диалогов в день.
- ~~Переделка фронтенда сверх необходимого.~~ Пересмотрено 2026-11-23: человек выбрал свой минималистичный
  интерфейс по макетам (`crm/design/`), см. этап D.

## Сквозные требования

- NFR1. Чистый сервер после `script/crm/provision.sh` поднимается `kamal setup` по `crm/docs/runbook.md`.
- NFR2. Перезагрузка сервера → всё поднимается само, сессии WhatsApp сохраняются.
- NFR3. Версии зафиксированы. Обновление upstream и деплой — по процедуре в `crm/docs/runbook.md`.
- NFR4. Секретов в репозитории нет.
- NFR5. Часовой пояс рабочих часов (`CRM_BUSINESS_TZ`) и пороги эскалаций настраиваются, значения из H4.
- NFR6. Память: весь стек в покое ≤1.3 ГБ RAM (`docker stats`), под типичной нагрузкой без OOM на сервере
  2 ГБ + swap.
- NFR7. Наш код живёт в `custom/` и `spec/custom/`. Каждая правка upstream-файла есть в
  `crm/docs/core-changes.md`.

## Этап D. Свой интерфейс по макетам — `in progress` (D1, D2 — ready for review)

Цель: вместо перегруженного интерфейса Chatwoot у команды простой кабинет, похожий на WhatsApp. Фрилансер
открывает его с телефона и сразу понимает, что делать. Менеджер видит всех клиентов, передаёт их фрилансерам,
подключает номера и заводит фрилансеров. Всё, чего нет в макетах, в новом интерфейсе не появляется.

Источники: ТЗ `crm/design/brief.md` (что и зачем) и макеты `crm/design/mockups/index.html` (как выглядит).
При расхождении прав ТЗ; если ТЗ молчит — макет; если молчат оба — спросить человека.

Сервер (Chatwoot + Evolution) остаётся. Новый интерфейс работает через его API и real-time-события, поэтому
изоляция фрилансера и скрытие номера (этапы 6, 6.1) действуют и для него без доработок.

### Как устроено (решения для исполнителя)
- Отдельное Vue 3-приложение в этом же репозитории: свой entrypoint Vite (`app/javascript/entrypoints/crm.js`),
  код в `app/javascript/crm/`. Только новые файлы — обновления upstream не конфликтуют. Открывается по своему
  адресу (например `/crm`) на том же домене, вход — та же авторизация Chatwoot. Маршрут — без правки upstream, если
  получится (добавить маршруты из `custom/config/`); иначе одна строка в `config/routes.rb` и запись в реестр.
- Стили — Tailwind (правило репозитория), цвета и размеры из макета переносятся в токены. Компоненты свои,
  простые; из старого интерфейса Chatwoot ничего не тянем, кроме API-клиентов и real-time-подключения, если они
  переиспользуются без зависимости от его стора.
- Тексты — vue-i18n, свои словари `ru` (по умолчанию) и `en` для нового приложения.
- Чего нет в API Chatwoot — дописываем на сервере в `custom/` (свои эндпоинты, модели, миграции), со спеками.
- Старый интерфейс `/app` на время перехода остаётся для админа. Фрилансеров после D4 туда не пускаем, а после
  этапа L старый интерфейс в боевую сборку не попадает вовсе.
- **Лёгкость — требование, а не пожелание.** Новое приложение грузит только свой код и только те данные, что
  нужны открытому экрану: без запросов «на всякий случай», без периодического опроса сервера (обновления — через
  WebSocket), без загрузки чужих модулей Chatwoot (аналитика, Captain, справочники функций и т. п.). Тяжёлое
  (плеер, предпросмотр, эмодзи, экраны менеджера для фрилансера) — отдельными частями, по требованию.

### Чего не хватает на сервере (сделать в `custom/`)
- **Скрытые чаты** — у каждого свои: отметка «скрыт» на пару пользователь–диалог; снимается, когда клиент пишет.
- **Статус сделки, поля сделки** — атрибуты диалога с проверкой допустимых значений; **метки клиента** — метки
  контакта Chatwoot, список правит админ.
- **Бриф** — приватная заметка с пометкой «бриф»; в чате закреплён последний бриф.
- **Номер ↔ фрилансер**: за каждым номером закреплён фрилансер (хранение — обосновать). **Передача** одним
  запросом: назначить, сохранить бриф, поставить статус «Передан».
- **Номера из интерфейса** (только менеджер): добавить (Evolution-инстанс + inbox, QR-код в ответе — на основе
  `Custom::Whatsapp::ConnectService`), переподключить, закрепить за фрилансером, отключить. Новых номеров без
  явного действия менеджера не появляется.
- **Фрилансеры из интерфейса** (только менеджер): создать (роль, флаг фрилансера, доступ к его номеру),
  **ссылка-приглашение** (одноразовая, 24 часа, по ней задаётся пароль — на механизме сброса пароля Devise, без
  почты), сменить номер, отключить доступ.
- **Шаблоны**: общие — `canned_responses` Chatwoot; личные — свои у каждого (своя таблица).
- **Настройки**: язык и тема у пользователя; у команды — рабочие часы, порог «ждёт ответа» (10 мин), причины
  отказа, метки. Время ожидания считается от `waiting_since` диалога.

## Этап 3. WhatsApp на сервере: Evolution API и первый номер — `blocked (H1)` · `[H5] [H6]`

Цель: WhatsApp работает на сервере так же, как сейчас на Mac. Клиент пишет на номер фрилансера, сообщение
появляется в Chatwoot, ответ из Chatwoot приходит клиенту обычным сообщением с этого номера. Mac для этого больше
не нужен.

Что делает исполнитель:
- [ ] **Запустить Evolution API на сервере рядом с Chatwoot.** Evolution — программа, которая держит связь с
      WhatsApp вместо телефона (как WhatsApp Web) и передаёт сообщения в Chatwoot. Требования:
      - доступна только самому Chatwoot, из интернета к ней не подключиться (через неё можно читать и
        отправлять сообщения от наших номеров);
      - после перезапуска и ребута сервера номера остаются подключены, QR заново сканировать не нужно;
      - не съедает память сервера: жёсткий лимит, замер записан в `crm/PROGRESS.md`.
      _Для исполнителя:_ Kamal accessory, отдельная БД и пользователь в Postgres, свой индекс/префикс Redis,
      API-ключ из секретов, volume для сессий, лимит памяти контейнера, порт не публикуется. Админка Evolution —
      только через SSH-туннель (`ssh -L`).
- [ ] **Связать Chatwoot и Evolution настройками.** То, что на Mac уже настроено: Chatwoot должен иметь право
      отправлять запросы в Evolution внутри сервера, Evolution не должен ничего слать своим разработчикам.
      _Для исполнителя:_ `SAFE_FETCH_ALLOW_PRIVATE_NETWORK=true` у Chatwoot (иначе его защита блокирует запросы во
      внутреннюю сеть), `TELEMETRY_ENABLED=false` и `CHATWOOT_BOT_CONTACT=true` у Evolution (см. этап M).
- [ ] **Подключение номера одной командой на сервере**, как на Mac: команда создаёт связку и присылает QR-код в
      Chatwoot. Описать в runbook, как перенести на сервер уже подключённые локально номера или подключить их заново.
      _Для исполнителя:_ `crm:whatsapp:connect` из этапа M, проверить на сервере.
- [ ] **Голосовые, фото и документы из Chatwoot доходят клиенту.** На Mac из-за адреса `localhost` они молча не
      уходили (см. `crm/docs/local-mvp.md`). На сервере адрес будет нормальный, но это надо проверить отправкой.
      _Для исполнителя:_ Evolution 2.3.7 скачивает вложение по `data_url` из `FRONTEND_URL` и отбрасывает адреса
      без доменной зоны (`isURL` из class-validator), ошибку в Chatwoot не возвращает. Проверить, что контейнер
      Evolution скачивает файл по `https://chat.<домен>`.
- [ ] **Клиент не видит имени агента в ответах.** Evolution умеет дописывать к сообщению имя агента. Команда
      подключения это уже выключает — проверить на тестовом номере, что подписи нет.
      _Для исполнителя:_ `chatwootSignMsg: false` в `Custom::Whatsapp::ConnectService`.
- [ ] **Инструкция в `crm/docs/runbook.md`:** как подключить номер, как переподключить, что делать, если номер
      разлогинился. Предупреждение: если основной телефон фрилансера ~14 дней не выходит в интернет, WhatsApp
      отключает связанные устройства, и номер придётся подключать заново.

Что делаешь ты:
- [ ] **Подключить первый номер** (H6): запускаешь команду по инструкции, сканируешь QR телефоном фрилансера
      (WhatsApp → Связанные устройства → Привязать устройство). Решаем вместе, нужна ли старая переписка
      из телефона в Chatwoot; решение записывается в `crm/PROGRESS.md`.
- [ ] **Проверить сценарии с тестового номера** (H5). Исполнитель ведёт таблицу «сценарий → результат» в
      `crm/PROGRESS.md`:
      - текст от клиента и ответ из Chatwoot;
      - фото, документ, голосовые — в обе стороны;

Критерии приёмки (как понять, что этап готов):

## Этап 6. Изоляция фрилансера: только его диалоги, без номера клиента — `ready for review`

Цель: агенты, отмеченные как фрилансеры (флаг из `config/crm/access.yml` или атрибут пользователя), видят
**только диалоги, назначенные на них или где они участники** (`ConversationParticipant`), и не видят телефон
клиента. Менеджеры и админы видят всё.

Почему доработка: в OSS Chatwoot агент видит **все** диалоги inbox'ов, в которых состоит, включая неназначенные
и назначенные на других (`app/services/conversations/permission_filter_service.rb`; проверено 2026-11-06 —
агент видел чужие назначенные диалоги). Ограничение «только мои» есть лишь в enterprise (кастомные роли,
`conversation_participating_manage`) — платно, не используем и не включаем в обход лицензии; пишем своё в
`custom/`, enterprise-код не копируем. А квалификация идёт в inbox'е номера фрилансера, так что без доработки он
видит всех входящих до передачи.

Задачи — видимость диалогов:
- [x] Определение «фрилансер» в одном месте (модельный метод или concern в `custom/`), используется всеми
      проверками ниже.
- [x] Список и фильтры: `Custom::Conversations::PermissionFilterService` (prepend; цепочка
      `Custom → Enterprise → OSS`) — для фрилансера `assignee = он` или участник. Покрывает
      `/conversations`, `/conversations/filter`, `/conversations/meta` и счётчики вкладок, unread counts.
- [x] Доступ по id: политика диалога (открытие, сообщения, вложения, заметки, действия по `/conversations/:id/*`)
      — 404/403 для чужого диалога, даже в своём inbox'е.
- [x] Поиск (`/search` и подтипы), контакты (`/contacts`, `/contacts/:id`, `/contacts/:id/conversations`,
      фильтры контактов): фрилансер видит только контакты своих доступных диалогов.
- [x] Action Cable: события диалогов и сообщений (`message.created`, `conversation.*`, typing и т. п.) уходят
      фрилансеру только по его диалогам. Сейчас они рассылаются всем участникам inbox'а — то есть содержимое
      чужих сообщений приходит в браузер.
- [x] Уведомления (in-app, будущий Telegram F5.2) — только по доступным диалогам.
- [x] Переназначение: диалог, снятый с фрилансера, исчезает у него (список, real-time), назначенный — появляется
      с полной историей и брифом.
- [x] Создание диалога фрилансером (`POST /conversations`) — только с контактами его диалогов и только на себя.

Задачи — номер клиента:
- [x] По списку утечек (исследование «Телефон клиента», этап 0) убрать номер на **сервере**: API-ответы, Action
