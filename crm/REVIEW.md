# Инструкция ревьюера

Ты независимый ревьюер. Твоя задача — найти, где этап **не** выполнен, выполнен небезопасно или хрупко
(в том числе по отношению к будущим обновлениям upstream). Отчёт исполнителя в `crm/PROGRESS.md` — это
заявление, а не доказательство. Кроме этого файла действуют правила ревью из корневого `AGENTS.md`
(разделы General Guidelines, Ruby Best Practices, Enterprise Edition Notes), с переопределениями из `crm/AGENTS.md`.

## Порядок

1. Прочитай `crm/AGENTS.md`, этап в `crm/PRD.md` со статусом `ready for review`, записи этапа в
   `crm/PROGRESS.md`, предыдущие `crm/reviews/stage-N.md` (при повторном ревью начни с них).
2. Посмотри изменения этапа: `git log` / `git diff <начало этапа>..HEAD`.
3. **Проверь каждый критерий приёмки сам.** Запусти спеки и линтеры, сделай запросы, зайди на сервер (только
   чтение и безопасные проверки). Для каждого AC зафиксируй, *как* проверял, и приложи короткий вывод.
4. Пройди чек-лист ниже.
5. Напиши `crm/reviews/stage-N.md` (шаблон ниже) и поставь этапу в `crm/PRD.md` статус `pass` или
   `changes requested`.

## Что тебе можно и нельзя

- Можно: читать всё, запускать `bundle exec rspec spec/custom ...`, rubocop, eslint; read-only команды
  на сервере (`kamal app details/logs`, `kamal accessory details`, `docker ps/stats`, `curl`, `ss -tlnp`,
  `ufw status`); вход под тестовыми учётками.
- С осторожностью: перезапуск или ребут, если этого требует AC, и только когда реальные клиенты не пострадают.
  Если номера уже в работе, спроси человека.
- Нельзя: править код или конфиги (кроме `crm/reviews/` и статуса в `crm/PRD.md`), пушить, писать реальным
  клиентам, удалять данные, менять секреты, цитировать `.env`.
- AC, который нельзя проверить без человека, отмечай как `NOT VERIFIED — нужен H#`, а не `PASS`.

## Чек-лист (каждый этап)

- [ ] Секретов нет в git (`git log -p <range> | grep -iE "token|password|secret|api_key"`), `.kamal/secrets`
      содержит только ссылки.
- [ ] Репозиторий публичный: в коммитах нет IP и домена сервера, реальных телефонов, имён, переписки,
      реального `config/crm/access.yml`.
- [ ] **Минимум правок upstream:** `git diff <base-tag>..HEAD --stat -- . ':!custom' ':!spec/custom' ':!crm'
      ':!config/deploy.yml' ':!.kamal' ':!script/crm' ':!.github/workflows/crm-*'` — каждый файл из этого
      списка есть в `crm/docs/core-changes.md` и помечен `# CRM:`. Нет ли способа сделать то же через `custom/`
      и `prepend_mod_with`?
- [ ] `enterprise/` не тронут, enterprise-функции не включены в обход лицензии.
- [ ] Версии образов зафиксированы точно, без `latest`.
- [ ] Ничего лишнего не торчит наружу. Нет новых внешних сервисов без согласия человека.
- [ ] Спеки осмысленные (проверяют поведение, включая права доступа и негативные сценарии), `spec/custom`
      и затронутые спеки upstream зелёные, rubocop чистый, i18n-строки есть в `en` и `ru`.
- [ ] Для задач и cron: нет гонок, повтор события не даёт дублей, работа ограничена по объёму.
- [ ] Ничто не ведёт к утечке номера клиента фрилансеру (особенно новые payload'ы уведомлений и событий).
- [ ] Память: свежие замеры `docker stats` в `crm/PROGRESS.md` укладываются в NFR6 (для этапов с деплоем).
- [ ] Документация в `crm/docs/` соответствует реальности: проверь 1–2 команды из неё.
- [ ] Отклонения от PRD записаны и обоснованы.

## Серьёзность замечаний

- **blocker** — AC не выполнен, уязвимость, потеря данных или сообщений, утечка номера или переписки,
  утечка секретов или реальных данных в публичный репозиторий. Этап не проходит.
- **major** — работает, но хрупко (в том числе ломается при обновлении upstream) или без документации для
  критичного действия. Этап не проходит, если замечаний больше одного или оно касается G1–G3.
- **minor** — стиль, мелкие улучшения. На вердикт не влияют.

## Шаблон `crm/reviews/stage-N.md`

```markdown
# Ревью этапа N — <название>

Дата: YYYY-MM-DD · Коммит: <sha> · Раунд: 1

## Вердикт: PASS | CHANGES REQUESTED

## Критерии приёмки
| AC | Результат | Как проверено (команда / действие) | Вывод (коротко) |
|---|---|---|---|
| ACN.1 | PASS / FAIL / NOT VERIFIED (H#) | ... | ... |

## Чек-лист
- [x] ... / [ ] ... — комментарий

## Замечания
1. **[blocker]** <файл:строка или компонент> — что не так, как воспроизвести, что ожидается.

## Ответ исполнителя
<по каждому замечанию: исправлено (коммит) / не согласен (почему)>
```
