# chatwoot_crm: контекст и правила для агентов

Это **наш форк Chatwoot** (копия upstream `chatwoot/chatwoot`, **публичный** репозиторий на GitHub). Корневой `AGENTS.md` (он же `CLAUDE.md`) —
правила upstream по качеству кода. Они действуют, кроме мест, которые этот файл явно переопределяет.
Прочитай этот файл целиком, потом `crm/PRD.md`, `crm/PROGRESS.md` (если есть), а ревьюер — ещё `crm/REVIEW.md`.

## Бизнес-контекст

Бизнес работает на входящих обращениях. Клиенты пишут в WhatsApp. У каждого фрилансера свой WhatsApp-номер,
номера принадлежат нам. Сначала с клиентом общается наш квалификатор (менеджер) и отсеивает нецелевых. Потом
клиента передают фрилансеру, и это должно быть **бесшовно**: клиент уверен, что с первого сообщения общался с
одним человеком. Менеджер, который ведёт сделку, видит переписку и после передачи.

Боли, которые решаем, в порядке важности:
1. **Нет надёжных уведомлений.** Сейчас человек вручную переключает аккаунты WhatsApp на Android и проверяет,
   нет ли новых сообщений. Пропущенное сообщение = потерянный клиент.
2. **Нет бесшовной передачи** клиента фрилансеру с сохранением всей истории.
3. Желательно: простая воронка (статусы сделки), скрытие номера клиента от фрилансера.
4. Позже: ИИ отвечает ночью и в нерабочее время.

**Анонимность важна.** Никакого WhatsApp Business / Meta Cloud API. Self-hosted. Минимум сторонних сервисов,
которые видят переписку или связывают проект с личностью владельца. Уже согласованы: GitHub (публичный
репозиторий, Actions, GHCR) и Telegram Bot API. Любой другой внешний сервис добавляется только после явного
согласия человека (через `crm/HUMAN.md`).

## Архитектура

```
Клиент (WhatsApp) ──► номер фрилансера (Android-телефон держит сессию)
                          │ linked device
                          ▼
                   Evolution API ──(встроенная интеграция)──► chatwoot_crm (наш форк)
                   [kamal accessory]                          роли web + sidekiq [kamal app]
                   1 instance = 1 номер                       1 inbox = 1 номер = 1 фрилансер
                                                              └─ custom/: наши доработки
                                                                 ├─ уведомления в Telegram, эскалации
                                                                 ├─ мониторинг WhatsApp-номеров
                                                                 ├─ скрытие номера клиента от фрилансера
                                                                 └─ (позже) ИИ-бот ночью
Accessories: PostgreSQL + pgvector (отдельные БД и пользователи для Chatwoot и Evolution), Redis.
kamal-proxy: HTTPS (Let's Encrypt) для chat.<домен>.
Хост: script/crm/watchdog.sh (systemd timer) шлёт алерт в Telegram, если упал сам Chatwoot или Sidekiq.
Сборка: GitHub Actions → образ в GHCR (публичный пакет, секретов в образе нет) → kamal deploy.
```

Модель доступа: фрилансер = агент Chatwoot, добавлен **только** в inbox своего номера. Менеджеры и админ — во все
inbox'ы. Передача клиента = назначение диалога на фрилансера + приватная заметка с брифом.

## Где живёт наш код

Главный принцип — **минимум правок в upstream-файлах**, иначе каждое обновление Chatwoot превращается в разбор
конфликтов.

- **`custom/`** — штатный механизм расширений Chatwoot (`ChatwootApp.custom?`, `ChatwootApp.extensions`).
  Модули в неймспейсе `Custom::` подключаются через существующие хуки `prepend_mod_with` / `include_mod_with`
  (например, `AsyncDispatcher.prepend_mod_with('AsyncDispatcher')` позволяет добавить свой listener). Структура
  повторяет `enterprise/`: `custom/app/{models,services,jobs,listeners,controllers,views}`, `custom/config/`,
  `custom/lib/`.
- **Спеки** — `spec/custom/`, по аналогии с `spec/enterprise/`.
- **Правки в upstream-файлах** допустимы, только если без них нельзя (например, подключить `custom/` в
  autoload-пути в `config/application.rb`, как это сделано для `enterprise/`). Каждая такая правка:
  помечена комментарием `# CRM: <зачем>` и внесена в реестр **`crm/docs/core-changes.md`** (файл, строки,
  причина, как проверить после обновления upstream).
- **Не трогаем `enterprise/`** (отдельная лицензия) и не включаем enterprise-функции в обход лицензии.
- **Документация и рабочие файлы агентов** — только в `crm/`.
- **Деплой**: `config/deploy.yml`, `.kamal/`, `.github/workflows/crm-*.yml`, `script/crm/`.

## Ветки и обновления upstream

- `upstream` = `chatwoot/chatwoot`, `origin` = наш публичный репозиторий `ruvaleev/chatwoot_crm`.
- Наша основная ветка `main` строится от **релизного тега** upstream (`vX.Y.Z` из `master`), а не от `develop`:
  `develop` нестабилен. Рабочие ветки — `feature/...` от `main`.
- Обновление: `git fetch upstream --tags` → merge нового релизного тега в `main` → разбор конфликтов по
  `crm/docs/core-changes.md` → полный прогон `spec/custom` и связанных спеков → деплой. Процедура описана
  в `crm/docs/runbook.md`.
- Upstream-воркфлоу GitHub Actions и dependabot отключены (H0). Наши воркфлоу называются `crm-*.yml`.

## Переопределения правил корневого AGENTS.md

- Linear-тикеты, PR в upstream и шаблоны PR Chatwoot **не применяются**. PR делаются внутри нашего репозитория
  (если человек их хочет), описание — по-русски, коротко.
- Conventional Commits — да. Префикс scope для наших изменений — `crm`, например `feat(crm): telegram alerts`.
- i18n: новые строки в `en.yml` / `en.json` **и** `ru.yml` / `ru.json` (наши пользователи русскоязычные; Crowdin
  в форке не работает). Тексты Telegram-уведомлений — через I18n с локалью из настроек, по умолчанию `ru`.
- Правило «Before adding/changing an OpenAI model» относится к функциям upstream. Для нашего ИИ-бота (этап 9)
  провайдер выбирает человек (H12).
- Остальное (качество кода, тесты, запреты на raw SQL, `Thread.new` и т. д.) **действует полностью**.

## Локальное окружение (Mac человека)

- Ruby 3.4.4 через **mise** (не rbenv, `rbenv init` из корневого `AGENTS.md` не выполнять). Проверка: `ruby -v`
  в корне репозитория должен показать 3.4.4. Если твой шелл показывает системный 2.6, используй
  `mise exec -- bundle exec ...`.
  Гемы установлены, `node_modules` установлены (pnpm). Node 24.
- PostgreSQL 18 (Homebrew, pgvector доступен) и Redis (Homebrew) уже запущены. Локальные настройки в `.env`
  (не коммитится, не показывать его содержимое в отчётах).
- **Диск почти полон**: на 2026-11-06 свободно ~5.6 ГБ. Перед установками, сборками ассетов и прочими тяжёлыми
  операциями делать `df -h ~`. Если свободно меньше 3 ГБ, остановиться и сказать человеку. Docker на Mac не
  ставить. Production-ассеты локально не собирать (это делает CI).
- Прогон всего suite Chatwoot локально долгий. Гоняй точечные спеки (`spec/custom`, затронутые спеки upstream),
  полный прогон — в CI (наш воркфлоу `crm-ci.yml`).

## Стек и соглашения деплоя

- **Kamal 2** (`config/deploy.yml`): сервис `chatwoot_crm`, роли `web` (за kamal-proxy, `ssl: true`,
  `host: chat.<домен>`) и `sidekiq`. Accessories: postgres (`pgvector/pgvector`, точный тег), redis, evolution.
  Образ собирается в GitHub Actions из `docker/Dockerfile` upstream и пушится в GHCR с тегом = git sha. Пакет публичный, как и репозиторий:
  секреты в образ не попадают (`.env` в `.dockerignore`, всё конфигурируется через ENV при запуске).
  Kamal деплоит готовый образ, не собирая его (проверить актуальный способ: `--skip-push`/`--version` и т. п.).
- Сторонние образы (Evolution API, Postgres, Redis) — с **точными** тегами, не `latest`. Версии сверять по
  официальным источникам, выбор записывать в `crm/PROGRESS.md`. Если сервер arm64, CI собирает arm64-образ.
- **Память — ресурс №1.** Сервер 2 ГБ + swap, весь стек в покое ≤1.3 ГБ RAM. Puma в single mode, 3–5 потоков,
  `SIDEKIQ_CONCURRENCY` 3–5, jemalloc или `MALLOC_ARENA_MAX=2`, ужатый Postgres, `maxmemory` у Redis, лимиты
  памяти контейнеров. Замеры `docker stats` — в `crm/PROGRESS.md`.
- Язык: код, коммиты — английский. Документация для людей (`crm/`), UI-строки для наших пользователей — русский.

## Жёсткие правила

1. **Секреты не коммитить никогда.** Значения — в менеджере паролей человека или ENV вне репозитория (Kamal
   берёт их через `.kamal/secrets`), в GitHub Secrets для CI и в контейнерах на сервере. `.env` не читать вслух и
   не цитировать. Перед каждым коммитом — `git diff --cached` на секреты.
2. **Репозиторий публичный — в нём только то, что не жалко показать.** Кроме секретов, в git не попадают:
   IP и домен сервера (в `config/deploy.yml` — через ERB из ENV, например `<%= ENV.fetch("CRM_HOST") %>`),
   реальные телефоны, имена фрилансеров и менеджеров, тексты переписки, `config/crm/access.yml` с реальными
   людьми (в git — только `access.example.yml`, реальный файл в `.gitignore` и на сервере или в секретах),
   скриншоты с данными. Фикстуры спеков — только выдуманные данные.
3. **Реальным клиентам ничего не отправлять.** Тесты исходящих — только на тестовые номера (H5).
4. **WhatsApp-номера беречь от бана:** никаких рассылок, первых сообщений на холодные номера, частых
   переподключений, нагрузочных тестов через WhatsApp.
5. **Сервер:** вход только по SSH-ключу, наружу открыты только 22/80/443. Accessories портов наружу не
   публикуют (сеть `kamal` или `127.0.0.1`). Менеджер Evolution — через SSH-туннель. Разрушительные действия
   (`kamal accessory remove`, удаление volumes, `docker system prune -a`, drop БД, пересоздание инстанса Evolution
   с подключённым номером) — только с явного подтверждения человека.
6. **Телеметрия и внешние вызовы:** отключить отправку данных в Chatwoot Hub (проверка версий, телеметрия),
   push-relay — по умолчанию выключен (H8). Новые исходящие интеграции — только с согласия человека.
7. **Блокер = стоп.** Если этап упирается в действие человека, допиши его в `crm/HUMAN.md`, поставь этапу
   статус `blocked (H#)` и остановись.
8. **Отклонения от PRD** — только с обоснованием в `crm/PROGRESS.md`. Новые технологии вне стека (compose, nginx,
   Caddy, отдельные сервисы) — только с согласия человека.
9. Не верить памяти про Chatwoot, Evolution API и Kamal: сверяться с кодом этого репозитория, официальной
   документацией и исходниками нужной версии.

## Роли

- **Исполнитель** берёт первый этап в `crm/PRD.md` со статусом `todo` (или `changes requested`), делает его на
  рабочей ветке, сам проверяет критерии приёмки, отмечает чек-боксы, ставит статус `ready for review`, пишет
  запись в `crm/PROGRESS.md` и коммитит. Один этап за сессию, если человек не сказал иначе.
- **Ревьюер** работает по `crm/REVIEW.md`. Код исполнителя не правит, пишет `crm/reviews/stage-N.md`.
